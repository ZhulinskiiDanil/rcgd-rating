# СПб Demonlist — MVP

Nuxt 4 + TypeScript + scoped SCSS + SQLite. Публичный лист, legacy, игроки, районы, карточки, история рейтинга, changelog и админка с проверкой permissions на сервере. Дизайн «Белые ночи»: светлый фон, синие акценты, крупные заголовки и превью; в шапке есть переключатель тёмной темы. Светлая тема включена по умолчанию, выбор сохраняется в cookie и применяется при серверном рендеринге. Локальные шрифты — Golos Text и Unbounded; их лицензии находятся в public/fonts. Стили компонентов — scoped SCSS, цвета обеих тем заданы общими переменными.

## Локальный запуск

Нужен Node.js 22.19+ (рекомендуется актуальный Node 22 LTS).

```sh
npm ci
npm run postinstall
cp .env.example .env
# Заполнить NUXT_SESSION_PASSWORD (случайная строка >=32 символов),
# HEAD_ADMIN_LOGIN и HEAD_ADMIN_PASSWORD (>=12 символов).
npm run bootstrap
npm run dev
```

Для Yarn Classic: `yarn install`, затем `yarn postinstall` и `yarn dev`. В проекте отключён автоматический запуск install-скриптов зависимостей (`.yarnrc`, `.npmrc`): better-sqlite3 13 уже содержит готовые бинарные модули, но Yarn 1 и некоторые версии npm ошибочно запускают для него node-gyp. Подготовка Nuxt выполняется явно командой `postinstall`. Visual Studio для поддерживаемых платформ не требуется. Не запускайте `npm rebuild better-sqlite3`. При добавлении зависимости, которой действительно нужен install-скрипт, его потребуется выполнить отдельно.

Не запускайте production-превью и dev-сервер одновременно на порту 3000. Если Nuxt выбрал 3001, остановите лишний сервер и перезапустите `yarn dev`, либо явно измените `APP_ORIGIN` на используемый адрес с портом 3001.

`APP_ORIGIN` задаёт адрес сайта, включая порт. Для локального адреса разрешены localhost, 127.0.0.1 и [::1] с тем же протоколом и портом; для публичного домена требуется точное совпадение. В подготовленной локальной копии это `http://127.0.0.1:3000`. В ней уже есть `.env` со случайным паролем head-admin и заполненная база. Учетные данные не публикуются в git/архиве. Для новой установки скопируйте `.env.example`.

Первый head-admin создаётся **только** из переменных окружения при запуске сервера или `npm run bootstrap`. Регистрация никогда не выдаёт прав. Повторный запуск не меняет пароль существующего head-admin и не повышает права существующего обычного аккаунта. После первого запуска в production удалите `HEAD_ADMIN_PASSWORD` из переменных окружения сервиса; хеш уже сохранён в базе.

```sh
npm run typecheck
npm test
npm run build
node scripts/smoke.mjs
npm start
```

Smoke-тест запускает production-сборку на 3100 с отдельной временной SQLite-базой. Рабочую базу он не изменяет. Не запускайте одновременно два smoke-теста.

## Начальные данные

Источники:

- [Таблица сообщества](https://docs.google.com/spreadsheets/d/1vSOs24s1nX9hWiwoy8qWSWh28CUKODectnBz14Vpx5M/edit?gid=626858444): 150 уровней; 56 игроков с шестью лучшими результатами; отдельные достижения 17 районов.
- [Global Demonlist API](https://demonlist.org/api-docs): все глобальные позиции и принятые рекорды привязанных игроков, с пагинацией.
- [Coreboard](https://coreboard.pythonanywhere.com/main/levels): `t` и `T`, строго первые 150 строк. Сопоставление по названию и явно заданным вариантам уровня, а не по порядковому номеру.

Готовые очки из таблицы не копируются: сайт пересчитывает их по согласованной формуле и актуальным процентам. Таблица импортируется один раз. Затем изменения вносятся в админке; очередная синхронизация не перезаписывает ручные решения. Для повторного **добавляющего** импорта используйте `node --env-file-if-exists=.env --import tsx scripts/import-sheet.ts`: существующие персональные записи остаются без изменений.

В таблице нет ID глобальных профилей и соответствия «игрок → район». Они намеренно не угадываются: откройте «Админка → Игроки» и заполните район и числовой ID из `demonlist.org/profile/123`. До привязки действуют импортированные результаты. Для игроков таблица содержит только шесть хардестов, а не полную историю прохождений. Вкладка «ПРОГРЕССЫ» не связывает дополнительные результаты с игроками, поэтому импортируются лишь прогрессы из их собственных шести ячеек.

Вкладка районов импортируется как отдельные достижения, без выдуманных персональных привязок. Когда персональные привязки будут заполнены, проверьте эти отдельные достижения: они не привязаны к конкретному игроку и не переезжают вместе с ним. Их можно удалить в админке. Повторы одного уровня в зачёте района не суммируются.

Для неоднозначных названий зафиксированы варианты: Thinking Space II/CairoX и версия CoCyMain (Legacy), Sakupen Circles/Diamond и Nick24. `Fever Dream` из таблицы сопоставлен с версией IcEDCave по его месту между Ouroboros и Visible Ray; `Knight of Thunder` → `Knights of Thunder`, `EXPLICT` → `EXPLICIT`. Сопоставление процентов можно уточнить в поле «Точное название в Coreboard». При ошибке или неоднозначности запись не получает чужие проценты: причина видна в журнале синхронизации.

## Редактирование на страницах

После входа аккаунт с нужными permissions видит кнопки редактирования рядом с уровнями, игроками, районами, рекордами, отдельными достижениями и новостями. Они открывают форму поверх текущей страницы. В ней можно изменить значения, сохранить их и сразу увидеть обновлённые данные и рейтинг. Несохранённые изменения требуют подтверждения закрытия; ошибки загрузки и сохранения показываются в форме.

На странице уровня «Добавить рекорд» подставляет этот уровень, на странице игрока — игрока, на странице района «Добавить достижение района» — район. Системные события changelog не редактируются: кнопка доступна только для вручную опубликованных новостей. Аватар собственного аккаунта head-admin можно изменить со страницы «Мой аккаунт».

Кнопки доступны по соответствующему праву: `levels:write`, `players:write`, `districts:write` (включая отдельные достижения), `records:write` или `news:write`. Управление аккаунтами доступно только head-admin. Публичное чтение остаётся доступным без регистрации. Видимость кнопок не заменяет проверку доступа: каждый изменяющий запрос проверяет актуальные permissions на сервере. Полная админка использует те же формы.

## Превью, видео и местные верификации

Кнопка редактирования уровня и раздел «Админка → Уровни» позволяют изменить обложку и видео любого уровня, в том числе связанного с глобальным листом. `previewImage` и `showcaseVideo` — ручные значения: синхронизация их не перезаписывает. Видео задаётся HTTP/HTTPS-ссылкой; на странице уровня появляется кнопка «Смотреть видео». Отдельная ссылка на глобальную верификацию посетителям не показывается.

Для обложки можно вставить ссылку или загрузить JPG, PNG, WebP до 5 МБ. После загрузки нужно сохранить запись. «Очистить» возвращает автоматическое превью: сначала обложка YouTube из выбранного видео, затем из исходного видео глобального листа, если своё видео не указано. Если подходящей ссылки или доступной картинки нет, показывается встроенная SVG-заглушка. Исходное глобальное видео хранится отдельно и не заменяется ручным выбором.

Оригинальная верификация — **первое прохождение для публикации уровня**, выполненное местным игроком. Это отдельные поля: игрок-верификатор, Санкт-Петербург или Ленинградская область и дата. Обычное достижение 100% не становится верификацией автоматически. Запись о верификации сама по себе не создаёт рекорд в рейтинге: для зачёта прохождения добавьте его в «Рекорды». Прежнее поле подтверждённого локального прохождения также не означает оригинальную верификацию.

На странице уровня первые викторы Санкт-Петербурга и Ленинградской области показаны двумя строками. Регион с более ранней известной датой расположен выше. Используются активные результаты 100% и регион района игрока; для дат также учитываются отдельные достижения районов. Если имя или дата не известны, интерфейс сообщает об этом. Игроков и даты из неполных исходных данных сайт не придумывает. Рядом с уровнями в рейтинге и на странице района показаны его викторы по дате прохождения; записи без даты идут последними.

Над региональными строками показан общий первый известный виктор, в том числе когда район игрока ещё не указан. Единственный известный виктор отображается и без даты. При нескольких прохождениях без дат показаны имена и пояснение, что определить порядок пока нельзя. При совпадении самой ранней даты отображаются все игроки с этой датой.

Загруженные изображения доступны по `/media/<uuid>.<расширение>`, а физически лежат в каталоге `media` рядом с SQLite-базой. Разрешены загрузки head-admin и аккаунтам с `levels:write` или `players:write`; формат и размер проверяются сервером. Удаление ссылки из записи не удаляет файл из хранилища.

## Даты прохождений

При добавлении или изменении ссылки на YouTube в рекорде форма автоматически получает дату публикации видео и подставляет её в дату достижения. В таблице источник отмечен как «Публикация видео · МСК». Если YouTube передаёт время публикации, календарная дата определяется в часовом поясе `Europe/Moscow`. Используется видео лучшего принятого результата: видео прогресса с меньшим процентом не становится источником даты прохождения 100%.

Дата, исправленная вручную, имеет приоритет: смена видео и синхронизация её не перезаписывают. Кнопка «Взять дату из видео» позволяет явно заменить ручное значение автоматически полученным. Ручная дата помечается как указанная администрацией. Для других видеосервисов и недоступных YouTube-видео дату нужно вводить вручную; если она неизвестна, запись можно сохранить без неё. Дата публикации не подменяется выдуманной датой фактического прохождения.

## Правила расчёта

- Местный список — уровни с подтверждённым прохождением в СПб/ЛО: из начальной таблицы, персональных рекордов или отдельных достижений района. Порядок следует текущим глобальным позициям. Первые 150 образуют основной лист (`main`). В Legacy попадают только уровни, которые уже были в основном листе и затем выпали из него. Прочие уровни остаются в каталоге (`catalog`); само наличие прохождения за пределами топа-150 не добавляет их в Legacy.
- Для прогресса `h = 1 + количество пройденных местных уровней выше этого уровня`. Сам прогресс не добавляет уровень в местный список.
- `f = h * 2 * (T/c) ** (ln(2) / ln(T/t))`. Учитываются только уровни текущего глобального топа-150 с корректными процентами Coreboard; `c < t` не учитывается, `c > T` ограничивается `T`.
- Шесть минимальных позиций; веса `[10,9,8,7,5,3]/42`. Пустое место — 150. Результаты хуже 150 не участвуют. Меньше балл — выше место. Внутренний расчёт без округления, в интерфейсе три знака.
- Один лучший результат на уровень. 100% заменяет прогресс. Ручной и импортированный результат объединяются по паре игрок/уровень, выбирается больший процент.
- Районы: только уникальные 100%, включая отдельно добавленные достижения. Наличие результатов за пределами местного топа-150 отображается, но они не улучшают балл.
- Одинаковый балл даёт одинаковое место. Фильтр игроков сохраняет место в общем рейтинге.

Дата Legacy — момент **обнаружения нового вылета** приложением. Уровни, которые уже находятся вне местного топа-150 при первом импорте, не получают архивный статус и выдуманную историческую дату. Возврат в основной лист очищает текущую дату вылета; прежние события остаются в changelog.

Для перехода со старого правила архива можно один раз выполнить из каталога проекта:

```sh
node --env-file-if-exists=.env --import tsx scripts/reset-legacy.ts
```

Команда переводит текущие Legacy-уровни в каталог и очищает их архивные метаданные. Карточки уровней, персональные рекорды и достижения районов сохраняются; рейтинговая формула не меняется. Сброс записывается в changelog. После него Legacy заполняется только новыми выпадениями из основного листа. Это служебная команда для осознанного сброса архива, её не нужно запускать при каждом обновлении сайта.

## Синхронизация

Существующие рекорды без ручной даты получают дату публикации видео при синхронизации. Для разового заполнения всех доступных дат без обновления глобального листа можно выполнить `node --env-file-if-exists=.env --import tsx scripts/backfill-record-dates.ts`. Команда использует видео конкретного результата, сохраняет ручные даты и выводит количество найденных и недоступных дат.

Сервер проверяет необходимость обновления каждую минуту; интервал — `SYNC_INTERVAL_MINUTES=60`, минимум 15 минут. Первый импорт начинается после запуска сервера. Ручной запуск — админка или `npm run sync`. `SYNC_ENABLED=false` выключает автоматический запуск.

Сначала загружаются и проверяются источники, затем изменения применяются транзакцией. Обрыв списка/пагинации не стирает базу. При сбое Coreboard сохраняются последние проценты и отмечается частичный запуск. Неудача импорта отдельного игрока не помечает его рекорды удалёнными. Повторный неизменённый импорт не добавляет события рейтинга.

Исчезнувший глобальный рекорд сохраняет результат и помечается `reviewNeeded`. Администратор может оставить его, снять отметку или выключить «Учитывать рекорд». Новые импорты не отменяют ручное выключение. При смене привязанного глобального профиля с уже импортированными рекордами API блокирует перепривязку во избежание смешивания игроков.

Есть блокировка параллельных синхронизаций с часовым сроком на случай аварийного завершения. В MVP рассчитано на **один экземпляр сервера** и один SQLite-том.

## Аккаунты и права

Логин/пароль: scrypt, зашифрованная HttpOnly-сессия через `nuxt-auth-utils`, ограничение попыток входа/регистрации, проверка Origin на изменяющих запросах. Сервер читает актуальные права из базы при каждом запросе: отзыв действует и для уже открытой сессии.

Head-admin выдаёт `levels:write`, `players:write`, `districts:write`, `records:write`, `news:write`, `sync:run` и может отключать обычные аккаунты. Право выдачи permissions не делегируется. Аккаунт и игрок — разные сущности.

Для Google/Discord нужны собственные OAuth-приложения и значения из `.env.example`. Redirect URL:

```text
https://ваш-домен/auth/google
https://ваш-домен/auth/discord
```

До настройки провайдера его кнопка входа скрыта. Аккаунты не объединяются по совпадению email: привязка запускается только из открытого аккаунта. Реальный OAuth redirect/callback проверяется после предоставления ваших client ID/secret.

Администратор с `players:write` может назначить аватар игроку; head-admin — любому аккаунту в разделе «Аккаунты и права», включая собственный. Доступны ссылка и загрузка изображения. Приоритет в карточке игрока: вручную заданный аватар игрока → аватар связанного аккаунта. В аккаунте: аватар, назначенный head-admin → Discord → Google → локально сгенерированный DiceBear Initials. Если у игрока нет привязанного аккаунта и своего изображения, аватар генерируется по его имени. Очистка ручного значения возвращает автоматический выбор. Изменение аватара head-admin не позволяет менять его защищённые права или отключать аккаунт.

## Railway

В репозитории есть Dockerfile и railway.json. Создайте сервис из этого репозитория, **одну реплику**, затем подключите постоянный volume по пути `/data`.

Обязательные переменные:

```text
DATABASE_PATH=/data/spb.sqlite
TRUST_PROXY=true
APP_ORIGIN=https://ваш-домен
NUXT_SESSION_PASSWORD=случайная-строка-минимум-32-символа
HEAD_ADMIN_LOGIN=выбранный-логин
HEAD_ADMIN_PASSWORD=случайный-пароль-минимум-12-символов
SYNC_ENABLED=true
SYNC_INTERVAL_MINUTES=60
```

При `DATABASE_PATH=/data/spb.sqlite` загруженные обложки и аватары сохраняются в `/data/media`, на том же постоянном volume. Монтируйте весь каталог `/data`, а не только файл базы: это сохраняет изображения между развёртываниями. Для переноса существующего сайта нужны и SQLite-база, и каталог `media`; относительные URL `/media/…` менять не требуется.

`TRUST_PROXY=true` включает чтение IP из заголовка доверенного Railway reverse proxy для ограничения попыток входа. При прямом доступе к Node оставьте `false`. Railway передаёт `PORT`; сервер слушает `0.0.0.0`. Healthcheck — `/api/health`. Данные создаются и импортируются при первом запуске. Секреты и локальная SQLite-база не попадают в Docker image. Делайте резервные копии всего volume штатными средствами Railway, включая изображения. Локальную проверку Docker image здесь выполнить нельзя: Docker в окружении отсутствует.

Не запускайте `nuxt generate`: нужны серверные маршруты и постоянная база. Деплой не выполнен; сервис подготовлен к нему.

## Структура

`app/components` и `app/pages` — Vue SFC, стили в каждом компоненте `<style scoped lang="scss">`. `shared/utils/rating.ts` — чистая формула; `server/services/sources.ts` — адаптеры; `sync.ts` — синхронизация; `changes.ts` — транзакционный пересчёт/история; `server/database` — схема SQLite; `server/api/admin` — проверяемые сервером изменения.

`npm audit` на момент сборки сообщает об upstream-зависимостях Nuxt tooling (`braces`, `node-forge` и цепочки зависимостей). Доступные исправления применены. Предлагаемый npm автоматический откат на старый Nuxt не применён. Перед публикацией повторите аудит на актуальном lockfile и обновите зависимости после появления совместимых исправлений.
